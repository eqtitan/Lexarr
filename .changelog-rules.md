# Commit → Changelog conventions

Lexarr uses [Conventional Commits](https://conventionalcommits.org) so the
history maps cleanly onto CHANGELOG sections. Entries are written by hand
under `## [Unreleased]` in the same PR as the change.

## Commit prefixes

| Prefix       | Example                                 | Changelog section | SemVer bump |
|--------------|-----------------------------------------|-------------------|-------------|
| `feat:`      | `feat: smart music search`              | **Added**         | minor       |
| `fix:`       | `fix: TV filter now excludes movies`    | **Fixed**         | patch       |
| `refactor:`  | `refactor: extract service layer`       | **Changed**       | patch       |
| `perf:`      | `perf: cache library lookups 60s`       | **Changed**       | patch       |
| `style:`     | `style: consistent button padding`      | **Changed**       | patch       |
| `remove:`    | `remove: Whisparr integration`          | **Removed**       | minor (or major if breaking) |
| `security:`  | `security: validate webhook tokens`     | **Security**      | patch       |
| `chore:`     | `chore: bump next.js to 16.2.1`         | **Chore** (collapsed in release notes) | patch |
| `docs:`      | `docs: README config section`           | **Chore**         | patch       |
| `test:`      | `test: cover artist detection edges`    | **Chore**         | patch       |

Anything without a prefix falls into **Chore** by default.

## When to bump which number

- **Patch** (`0.5.0` → `0.5.1`) — bug fixes, internal refactors, docs, tests,
  anything that keeps the contract (API shape, env vars, DB schema) stable.
- **Minor** (`0.5.0` → `0.6.0`) — new backwards-compatible features. New env
  vars that are optional; new DB columns that are nullable; new API routes.
- **Major** (`0.x.y` → `1.0.0`) — crossing the stability line. A user
  upgrading MUST read the release notes. Breaking API changes, required env
  var changes, renamed/dropped DB columns.

**Pre-1.0 relaxation:** minor bumps may include breaking changes during
`0.x`. Always document breaking changes under a `### Breaking` section
regardless of bump type.

## BREAKING CHANGES

If a commit introduces a breaking change, include `BREAKING CHANGE:` in
the commit body, and list it under `### Breaking` in the CHANGELOG even
when the bump is minor/patch:

```
feat: move releaseType off Request into a dedicated table

BREAKING CHANGE: SQL migration required. Existing Request rows have
releaseType dropped; the new ReleaseMonitoring table carries it.
```

## Cutting a release

`deploy.ps1` is the one release path. A release is an ordinary PR:

1. Branch `chore/release-X.Y.Z` from master.
2. Bump the version: `npm version X.Y.Z --no-git-tag-version` (updates
   `package.json` and `package-lock.json`).
3. In `CHANGELOG.md`, rename `## [Unreleased]` to `## [X.Y.Z] — <date>`
   and add a fresh empty `## [Unreleased]` above it.
4. Open the PR (`chore: release vX.Y.Z`), wait for green CI, merge.
5. Tag the merge commit so releases are findable in git:
   `git tag -a vX.Y.Z <merge sha> -m "Lexarr X.Y.Z" && git push origin vX.Y.Z`.
6. Ship it: `.\deploy.ps1 -Rehearse` (add `-RehearseName TEST4LexArr
   -KeepRehearsal` to test it by hand first), then `.\deploy.ps1`, which
   updates the existing `lexarr` container or installs it fresh, and removes
   the rehearsal containers once it is live. Each production deploy also
   pushes a `deployed/<time>-<sha>` tag and gets a line in the operator's own
   deploy log.
7. Publish a GitHub Release for the tag, with that version's CHANGELOG
   section as the notes:
   `gh release create vX.Y.Z --title "Lexarr X.Y.Z" --notes-file <section>`.

Pushing the tag in step 5 also starts `.github/workflows/publish-image.yml`,
which checks the tag matches `package.json`, builds the image, proves it
starts, and pushes `ghcr.io/eqtitan/lexarr:X.Y.Z`, `:X.Y` and `:latest`. The
tag must be created after the workflow is on master. Watch the run; a
failed run leaves the tag in place but no image.
