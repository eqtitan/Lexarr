# Commit → Changelog conventions

Lexarr uses [Conventional Commits](https://conventionalcommits.org) so that
`npm run release` can generate CHANGELOG entries automatically.

## Commit prefixes

| Prefix       | Example                                 | Changelog section | SemVer bump |
|--------------|-----------------------------------------|-------------------|-------------|
| `feat:`      | `feat: smart music search`              | **Added**         | minor       |
| `fix:`       | `fix: TV filter now excludes movies`    | **Fixed**         | patch       |
| `refactor:`  | `refactor: extract service layer`       | **Changed**       | patch       |
| `perf:`      | `perf: cache library lookups 60s`       | **Changed**       | patch       |
| `style:`     | `style: consistent button padding`      | **Changed**       | patch       |
| `remove:`    | `remove: Whisparr integration`          | **Removed**       | minor (or major if breaking) |
| `security:`  | `security: validate webhook tokens`     | **Security**      | patch       |
| `chore:`     | `chore: bump next.js to 16.2.1`         | **Chore** (collapsed in release notes) | patch |
| `docs:`      | `docs: README config section`           | **Chore**         | patch       |
| `test:`      | `test: cover artist detection edges`    | **Chore**         | patch       |

Anything without a prefix falls into **Chore** by default.

## When to bump which number

- **Patch** (`0.5.0` → `0.5.1`) — bug fixes, internal refactors, docs, tests,
  anything that keeps the contract (API shape, env vars, DB schema) stable.
- **Minor** (`0.5.0` → `0.6.0`) — new backwards-compatible features. New env
  vars that are optional; new DB columns that are nullable; new API routes.
- **Major** (`0.x.y` → `1.0.0`) — crossing the stability line. A user
  upgrading MUST read the release notes. Breaking API changes, required env
  var changes, renamed/dropped DB columns.

**Pre-1.0 relaxation:** minor bumps may include breaking changes during
`0.x`. Always document breaking changes under a `### Breaking` section
regardless of bump type.

## BREAKING CHANGES

If a commit introduces a breaking change, include `BREAKING CHANGE:` in
the commit body. The release script will surface these even when the bump
is minor/patch:

```
feat: move releaseType off Request into a dedicated table

BREAKING CHANGE: SQL migration required. Existing Request rows have
releaseType dropped; the new ReleaseMonitoring table carries it.
```

## Sample of a clean release

```
git log v0.4.8..HEAD --oneline
  a99b66e fix: TV/Movies chips now actually filter by type
  6c90bf4 fix: request button state syncs without refresh
  21b96e2 fix: Dockerfile copies public/, favicon now loads

npm run release -- patch
→ 0.4.8 → 0.4.9 (three patches; CHANGELOG gets "### Fixed" section)
```

## What `npm run release` does and doesn't do

**Does:**
- Bumps `package.json` version
- Inserts a new CHANGELOG block above `## [Unreleased]`
- Commits `chore: release vX.Y.Z`
- Creates an annotated git tag `vX.Y.Z`

**Doesn't (by design — manual review points):**
- Push to git
- Build or push Docker images
- Create GitHub Releases (intentional while repo is private)

See `scripts/release.js` for the full flow.
